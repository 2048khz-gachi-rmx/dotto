## Purpose

Hardens sandbox containers against breakout and privilege escalation, prevents credential leakage between bot and sandbox, confines file paths to the sandbox namespace, and adds a docker-socket-protector sidecar to limit the bot's Docker API access.

## Threat Model

Every guarantee in this spec assumes **the bot process and its container are not compromised**. That assumption is load-bearing, not incidental:

- the per-caller storage directory must be bind-mounted by host path, so the bot's own container necessarily has read/write access to every caller's files;
- the bot holds the Docker API (through the socket protector) and mints the per-container tokens, so it could create, inspect, or drive any sandbox it wants;
- the bot holds the Discord token, downloader cookies, DB credentials and S3 keys.

The sandbox boundary protects the host and the bot's secrets from **commands generated by the LLM**; it does not protect callers from a compromised bot. Hardening the bot process itself (image provenance, dependency updates, least-privilege deployment) is out of scope here.

## ADDED Requirements

### Requirement: Container Hardening
Every sandbox container SHALL be created with the following security settings:
- Read-only root filesystem
- All Linux capabilities dropped
- `no-new-privileges` security option enabled
- tmpfs mounts at `/work` (sized by `WorkTmpfsMb`) and `/tmp` (64MB)
- A hard process-count limit of 256 PIDs
- `dotto-sandbox=true` label applied
- `dotto-session-id={sessionId}` label applied
- `--rm` for auto-removal on stop
- No Docker socket mounted

#### Scenario: Hardened container created
- **WHEN** a sandbox container is created
- **THEN** it has `ReadonlyRootfs: true`, `CapDrop: ALL`, `SecurityOpt: ["no-new-privileges:true"]`, and a `PidsLimit` of 256

#### Scenario: No Docker socket mounted
- **WHEN** a sandbox container is created
- **THEN** the Docker socket is NOT mounted in the container

### Requirement: Credential Isolation
The sandbox container SHALL NOT have access to the Discord bot token, the yt-dlp cookies file, database credentials, S3 access keys, or LLM API keys. Its environment SHALL contain only:
- `SANDBOX_TOKEN` — the random per-container API token
- `SANDBOX_STORAGE_QUOTA_MB` — the persistent-storage quota

#### Scenario: Only sandbox-owned environment variables
- **WHEN** a sandbox container is created
- **THEN** its environment contains only `SANDBOX_TOKEN` and `SANDBOX_STORAGE_QUOTA_MB`

#### Scenario: Bot secrets never enter the sandbox
- **WHEN** the bot configures a sandbox container
- **THEN** it does not pass the bot token, cookies path, connection string, or S3 credentials

### Requirement: Token Authentication
Every sandbox request SHALL require `X-Sandbox-Token`. The token SHALL be generated randomly per container, compared in constant time, and discarded with the container. An unconfigured token SHALL fail closed (HTTP 503).

#### Scenario: Wrong token rejected
- **WHEN** a request supplies a token that does not match the container's token
- **THEN** the sandbox responds with HTTP 401 and executes nothing

#### Scenario: Token is unique per container
- **WHEN** two sandbox containers are created
- **THEN** each has a different `SANDBOX_TOKEN`

### Requirement: Docker Socket Protection
The bot SHALL communicate with the Docker daemon through `docker-socket-protector`, which SHALL whitelist only the following Docker API endpoints:
- `POST /containers/create`
- `POST /containers/{id}/start`
- `GET /containers/{id}/json`
- `GET /containers/json`
- `DELETE /containers/{id}`
- `POST /containers/{id}/stop`

Docker exec endpoints are NOT whitelisted — the bot communicates with sandboxes via HTTP (the Python server), not Docker exec. Image pulls are NOT whitelisted; the sandbox image SHALL be pre-pulled by a separate compose service before the bot starts.

#### Scenario: Unauthorized endpoint rejected
- **WHEN** the bot attempts to call `POST /images/create` (pull image)
- **THEN** the socket protector rejects the request

### Requirement: Network Isolation
Sandbox containers SHALL be attached to the dedicated `sandbox` network, not the network carrying the bot's backend services. The socket-protector SHALL live on a separate internal network and SHALL NOT be reachable from sandboxes, directly, through the bridge gateway, or through a published host port.

#### Scenario: Sandbox cannot reach backend services
- **WHEN** a sandbox container is created in production
- **THEN** it is attached only to the `sandbox` network and cannot reach PostgreSQL

#### Scenario: Sandbox cannot reach the Docker proxy
- **WHEN** a sandbox container is created
- **THEN** it has no route to the socket-protector, including via the bridge gateway

### Requirement: Egress Containment
Sandboxes SHALL have outbound internet access (curl, package-free searches) but SHALL NOT reach the host, the LAN, link-local/metadata addresses, CGNAT ranges, the socket-protector, or other containers' published ports.

#### Scenario: Internet egress still works
- **WHEN** a sandbox fetches a public URL
- **THEN** the request succeeds

#### Scenario: LAN and metadata endpoints are blocked
- **WHEN** a sandbox connects to a LAN address or a link-local address
- **THEN** the connection is dropped

#### Scenario: Published host ports are blocked
- **WHEN** a sandbox connects to the bridge gateway on a port published by another container
- **THEN** the connection is dropped

### Requirement: Egress Filter Installation
The `sandbox` network SHALL pin a stable bridge name (`br-sandbox`) and explicit subnet so host rules can target it. A host-side filter SHALL drop non-public destinations and NEW host-bound connections on that bridge; same-bridge traffic SHALL be excluded because `br_netfilter` routes it through `FORWARD`. The filter SHALL be shipped as a compose sidecar (`sandbox-firewall`, host network + `NET_ADMIN`, image from `.docker/sandbox-egress/`) that applies the rules at startup and removes them on shutdown, so the stack is self-contained and survives restarts. PostgreSQL SHALL be published on `127.0.0.1` only. The rules are IPv4-only, so the sandbox network SHALL keep IPv6 disabled; enabling it removes the containment.

#### Scenario: Bot can still reach the sandbox API
- **WHEN** the bot calls the sandbox API over the shared bridge
- **THEN** the request succeeds despite the egress filter

#### Scenario: Egress filter is owned by the stack
- **WHEN** the compose stack is started
- **THEN** the `sandbox-firewall` sidecar applies the rules without any host unit or manual step

#### Scenario: Filter is re-applied on restart
- **WHEN** the `sandbox-firewall` container restarts
- **THEN** it re-applies the rules before exiting or idling

#### Scenario: Missing egress filter degrades safely
- **WHEN** the sidecar is not running
- **THEN** PostgreSQL remains unreachable because it is only published on loopback

### Requirement: Path Confinement
All sandbox file paths SHALL be confined to `/work` and `/storage`. The sandbox server SHALL resolve paths with `realpath` so symlinks cannot escape. For writes the *parent* directory is resolved, because the target file may not exist yet; a pre-existing symlink as the final path component is therefore not followed-but-also-not-resolved, which is acceptable because anything it could point at outside the allowed roots is either on the read-only rootfs or in the `64MB` `/tmp` tmpfs. The bot SHALL NOT resolve a sandbox-authored path in its own filesystem namespace.

The host-facing `UploadFile` tool SHALL reject paths that do not start with `/work/` or `/storage/`, and SHALL reject any path containing `..`. `DownloadMedia` SHALL let the server generate and deduplicate filenames rather than trusting a bot-computed path.

#### Scenario: Upload tool rejects path traversal
- **WHEN** the LLM calls `UploadFile` with a path containing `..`
- **THEN** the tool returns an error without uploading

#### Scenario: Symlink cannot escape the sandbox roots
- **WHEN** a file operation targets a symlink pointing outside `/work` and `/storage`
- **THEN** the sandbox server rejects the request

### Requirement: Bot-Owned Temp Files
Files that the handler must hold after the container stops SHALL be copied into a bot-owned temporary file at a bot-chosen path. The name SHALL be a bot-generated random GUID salted with the sandbox-supplied *extension* (which is validated as an extension only, never used as a path); the sandbox never supplies the path or the base name.

#### Scenario: Discord attachment uses a bot-generated temp name
- **WHEN** the handler buffers a sandbox file for Discord delivery
- **THEN** the temporary file is `dotto-ai-{guid}{extension}`, with the GUID generated by the bot and the extension taken from the sandbox file name
- **AND** no directory component from the sandbox path is used
